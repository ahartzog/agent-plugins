## External Retrieval (2.16.0 follow-ons)

- [x] **Live store search fallback — delivered in 2.19.0.** When the corpus is insufficient for a question (nothing matched, or a matched row cannot answer a recency-shaped question), the RLDP dispatches a scoped subagent to search the live store, ranks candidates by path-inferred metadata, cites only opened documents, and promotes opened documents into the covering `type: index` catalog marked `discovered_via: search`. Scoped to declared store roots by default; tenant-wide requires explicit user direction. See `skills/apiary/references/external-retrieval-search-design.md` and `protocol/routing-protocol.md` §Search. Audit gained a catalog-staleness detection check (`references/mode-audit.md` § Catalog Staleness Check) as the read-side half.
- [ ] **Local cache for fetched external documents.** §Resolve re-fetches on every Ask; two sessions asking about the same ICD each pay auth + download + parse, and a large binary pays it twice in one session. Design questions: where does a cache live (not `knowledge/` — `knowledge-schema.md` requires read-time caches be disposable and out of knowledge content), what is the invalidation signal (store-reported mtime/etag vs a TTL vs `decay:`), and how does it interact with `sources/`, which is already the *durable* fetch-once surface for material worth keeping. Likely shape: a gitignored per-user cache keyed by resolved URL, distinct from `sources/` (permanent, committed, indexed). Watch the classification boundary — a cache writes fetched content to disk, which is a different exposure question than reading it into a turn. **(Still open — §Search's verification read fetches a winner twice, which this would collapse to one fetch plus a validation check; not resolved by 2.19.0.)**
- [ ] **Migrate store-relative catalog rows to absolute URLs.** Absolute URLs are now the preferred locator form (`knowledge-schema.md` § Store Roots), but existing catalogs are overwhelmingly store-relative folder paths — an artifact of folder trawls run when nothing could resolve them. Worth a one-time pass per Hive: resolve each row once, write the durable URL back. Needs a decision on folder-level rows, which have no single URL until a file is chosen. Until then both forms resolve, so this is cleanup, not a blocker.
- [ ] **Fetch-disposition on the entry** (`load` | `cite-only` | `query-live`). Some material should never be mirrored (live systems — query it every time) and some should be named but not fetched (classification-restricted). Both conventions already exist as prose in child Hives. Deferred from 2.16.0 because the main driver is classification, which that change scoped out. Revisit with the classification-exposure question (reading CUI into an UNCLASSIFIED Hive's context is policy, not plumbing). **Its classification-exposure driver is now live:** §Search's augment path treats catalog rows as a cache to be revalidated globally, which is exactly what a per-entry `query-live` disposition would state locally. §Search does **not** resolve this debt — it applies the assumption corpus-wide rather than letting an entry declare it — so the per-entry disposition is still worth having.
- [ ] **Corpus-wide re-trawl automation.** §Search repairs the corpus one asked question at a time and cannot surface a document nobody asks about; the 2.19.0 audit check *detects* catalog staleness (`references/mode-audit.md` § Catalog Staleness Check) but only recommends a re-trawl — it does not run one. Open work: a mechanism that, on a stale-catalog signal, re-trawls the store roots a `type: index` catalog declares and proposes the delta as promotions, closing corpus-wide drift the way §Search closes per-question misses. Needs a decision on where it runs (Parliament vs a scheduled job) and how it dedups against existing rows.
- [ ] **Re-home `tool-tiers.md` as a resolver registry.** Its content is Meridian-wide reference data (which tool reaches which store), not mechanics and not per-Hive domain — a third layer the two-layer ownership model has no slot for. Today its extension mechanism tells each Hive to hand-edit a copy of a canonical table in a child-owned file, which is the drift pattern the RLDP consolidation (2.12.0) fixed for routing. Split: Meridian-standard resolvers referenced from upstream, Hive-unique resolvers registered additively.

## Hive Configuration Modes (second-brain unification)

The core idea: second-brain is a local-mode Hive. Instead of maintaining two parallel knowledge management systems with convergently-evolved schemas, make the Apiary protocol configurable so a Hive can run in different modes:

- [ ] **`hive.yml` protocol toggles.** Add a `protocols:` block where individual protocol files can be enabled/disabled. A local-only Hive (today's second-brain) would disable `parliament`, `sentinel`, and `signal` while keeping `knowledge-schema`, `document-quality`, `workflows`, `learning-loops`, and `audit`. Parliament requires git remote; a local Obsidian vault doesn't have one.
- [ ] **Storage backend abstraction.** Today Hives assume a git repo. A local Hive might be an Obsidian vault, a directory of markdown files, or a Claude memory folder. The protocol files shouldn't hardcode git operations — abstract `push`, `commit`, `inbox` into operations that each backend implements.
- [ ] **Second-brain as Apiary L1-L3 on-ramp.** second-brain's maturity model (L1-L5) maps naturally to Apiary protocol adoption: L1-L2 = local-only with manual maintenance, L3 = reference-library + audit, L4 = Parliament + automated contribution processing, L5 = cross-Hive federation. Document this graduation path.
- [ ] **Retroactive schema compatibility.** Ensure existing second-brain knowledge files (which already use the same frontmatter fields) are valid Apiary knowledge files with zero migration. The schemas are already compatible — formalize and test this.
- [ ] **Protocol inheritance model.** When Apiary ships a new protocol file (like `document-quality.md`), all Hives — including local-mode ones — should be able to opt in. The `hive.yml` `upstream_version` + upgrade mechanism already handles this for remote Hives. Extend it to work for local Hives that don't have Parliament.
