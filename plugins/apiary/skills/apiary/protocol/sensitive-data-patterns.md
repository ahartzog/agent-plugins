# Sensitive Data Patterns — Sentinel Source of Truth

**Machine-readable source of truth:** [`assets/sentinel-patterns.json`](../assets/sentinel-patterns.json). This file is the human-readable companion — useful for review and discussion, but the JSON is what runs.

Patterns are consumed by:

1. **Pre-push hook** (generated by `assets/generate-hook.sh`) — installed at `{HIVE_ROOT}/.githooks/pre-push` by operate-mode Step 0. First defensive layer; runs locally on every push, blocks before content reaches the remote.
2. **Parliament Sentinel intake** (`custodian-workflow.md` § 0) — second defensive layer; catches anything that bypassed the hook (manual file drops, `--no-verify` pushes, contributions from non-Apiary tooling).

Both layers MUST read from `assets/sentinel-patterns.json`. The tables below mirror the JSON for review purposes — if they disagree, **the JSON wins**.

A Hive may add a **third** layer of its own — see [Hive-specific hardening](#hive-specific-hardening) below. It can only tighten, never loosen.

---

## Why two layers

Pre-push catches the bulk of contributor-side mistakes before they reach the remote at all. Parliament Sentinel catches anything pre-push missed (e.g., contributions written by a different agent, manual file drops, files that bypassed the session push procedure). The same pattern set is enforced at both layers because the threat model — credentials/PII landing in a knowledge repo — is the same regardless of who or what authored the file.

---

## Patterns

Patterns are described as named regex groups so each layer can produce a consistent match report (pattern name + line numbers).

### Credentials

The `(?i)` prefix is not ERE — the generator strips it and compiles the pattern with `grep -iE`.
Inside a POSIX bracket expression a backslash is **literal**: write character classes with
`[[:space:]]` (never `\s`) and place `-` last (never `\-`). Every pattern must ship with a
positive detection test in `tests/sentinel.test.sh`.

| Pattern name | Regex (POSIX ERE) | Notes |
|---|---|---|
| `credential.password-literal` | `(?i)\bpassword[[:space:]]*[:=][[:space:]]*["'\x60]?[^[:space:]"'\x60]{4,}` | Catches `password: foo`, `Password=`, `password = "..."`. Min 4 chars after the assignment to reduce noise. |
| `credential.api-key-literal` | `(?i)\bapi[-_]?key[[:space:]]*[:=][[:space:]]*["'\x60]?[A-Za-z0-9_-]{16,}` | API key assignments with ≥16-char value. |
| `credential.token-literal` | `(?i)\b(auth|access|bearer|secret)[-_]?token[[:space:]]*[:=][[:space:]]*["'\x60]?[A-Za-z0-9_.-]{20,}` | Bearer/auth/access/secret tokens with ≥20-char value. |
| `credential.aws-access-key` | `\bAKIA[0-9A-Z]{16}\b` | AWS access key ID. |
| `credential.aws-secret-key` | `(?i)\baws[-_]?secret[-_]?access[-_]?key[[:space:]]*[:=][[:space:]]*["'\x60]?[A-Za-z0-9/+=]{40}` | AWS secret access key (40-char). |
| `credential.private-key-block` | `-----BEGIN (RSA |EC |DSA |OPENSSH |PGP )?PRIVATE KEY-----` | Any PEM/PKCS private key header. |
| `credential.gcp-key-json` | `"private_key_id"[[:space:]]*:[[:space:]]*"[a-f0-9]{40}"` | GCP service-account key JSON fingerprint. |
| `credential.connection-string` | `(?i)\b(jdbc|postgres|postgresql|mysql|mongodb\+?srv?|redis)://[^[:space:]@]+:[^[:space:]@]+@` | URL-form connection string with embedded password (`scheme://user:pass@host`). |
| `credential.github-pat` | `\bghp_[A-Za-z0-9]{36}\b` | GitHub personal access token (classic format). |
| `credential.slack-token` | `\bxox[abprse]-[A-Za-z0-9-]{10,}` | Slack API tokens, incl. `xoxe-` refresh tokens. |
| `credential.github-token-fine-grained` | `\bgithub_pat_[A-Za-z0-9_]{22,}\b` | GitHub fine-grained PAT. |
| `credential.github-token-oauth` | `\bgh[osur]_[A-Za-z0-9]{36}\b` | GitHub `gho_`/`ghs_`/`ghu_`/`ghr_` tokens. |
| `credential.azure-account-key` | `(?i)\bAccountKey=[A-Za-z0-9+/=]{40,}` | Azure storage connection-string key. |
| `credential.azure-sas-sig` | `[?&]sig=[A-Za-z0-9%+/=]{32,}` | Azure SAS signature in a URL. FP risk on shared links — but a SAS link IS a bearer credential; override genuinely public samples. |
| `credential.jwt` | `\beyJ[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}` | Signed JWT (three base64url segments). |
| `credential.bearer-header` | `(?i)\bauthorization:[[:space:]]*bearer[[:space:]]+[A-Za-z0-9_./+=-]{20,}` | `Authorization: Bearer <token>` with a literal value. |

### PII

| Pattern name | Regex (POSIX ERE) | Notes |
|---|---|---|
| `pii.ssn` | `\b[0-9]{3}-[0-9]{2}-[0-9]{4}\b` | US Social Security number. |
| `pii.us-phone` | `\b(\+?1[-. ]?)?\(?[2-9][0-9]{2}\)?[-. ][0-9]{3}[-. ][0-9]{4}\b` | US phone number. Excludes leading `1-1xx` and `0xx` area codes. |

**Email addresses are explicitly NOT in this list.** Professional work emails are expected in stakeholder/people knowledge files (per `security-policy.md` § PII Rules).

## Hive-specific hardening

The pattern set above is deliberately **universal** — it detects things that look the same in every domain. A credential looks like a credential regardless of what the Hive is about, which is why these patterns live upstream and every Hive gets them.

Domain disclosure risk is not universal. A Hive whose subject matter is not sensitive on its face but whose *application* is controlled can leak without matching any pattern here. A **synthetic** illustration — invented for a test fixture, not drawn from any real program:

> "our customer needs a 12 minute revisit cadence against their GEO belt targets"

No credential, no PII, no marking — every regex above passes it, and that shape of sentence is precisely what must not land. Detecting it needs domain judgement, not a pattern.

A Hive declares such a check as a **gate extension** (`extensions.gates` in `hive.yml`), which `assets/generate-hook.sh` bakes into the generated pre-push hook. Authoring contract: [`references/authoring-gate-extensions.md`](../references/authoring-gate-extensions.md).

**Gates cannot weaken this file.** The generated hook evaluates the pattern scan first and exits on match before invoking any gate, so:

- a gate returning success cannot rescue a file that matched a built-in pattern;
- a gate cannot disable the Sentinel, reorder itself ahead of it, or narrow the file list it sees;
- the only thing a gate can do is block something the Sentinel allowed.

This is what makes gates safe to add without upstream review — a Hive can only raise its own bar. It is the direct application of plugin-root `DESIGN-GOALS.md` principles 3 (extensions are additive only) and 4 (Sentinel is non-negotiable).

**Choosing where a check belongs:**

| The check is… | Put it… |
|---|---|
| A new credential or PII format any Hive could encounter | Here — `assets/sentinel-patterns.json`, so all Hives benefit |
| Semantic (needs judgement about meaning) or specific to one domain's term list | A gate extension in that Hive |

Gates may require runtimes beyond bash/grep/git (a model CLI, python3). That is the Hive's own dependency to declare and document — the same footing as opt-in connectors under plugin-root `DESIGN-GOALS.md` principle 9, and a real cost to weigh, since every contributor to that Hive then needs the toolchain to push.

## Disposition

When the pre-push hook or Parliament Sentinel matches a pattern, the layer-specific runbook applies:

- **Pre-push hook:** the hook itself only detects and reports — it has no UI. On match it exits non-zero and the agent runs the override-approval flow in `references/pre-push-sentinel.md`. Default = hard block; user may approve an override via `AskUserQuestion` (only available in main agent context — subagents cannot override).
- **Parliament intake:** see `custodian-workflow.md` § 0. Hard reject → quarantine; no override (the user is not in the loop). Parliament does honor `sentinel_override` frontmatter recorded by the pre-push flow — if a match is fully covered by an existing override, Parliament logs it instead of quarantining.

## Adding a pattern

Patterns are protocol changes — modifying this file or `assets/sentinel-patterns.json` requires the same CODEOWNER-reviewed PR as any `PROTOCOL/` change (per `security-policy.md` § Repository Protection Model). When adding a pattern:

1. Add an entry to `assets/sentinel-patterns.json` (the runtime source of truth).
2. Mirror it in the table above for human review.
3. Bump the apiary plugin minor version (operate-mode Step 0 re-copies the patterns file on every invocation, so live Hives pick up the change automatically).
4. Note any false-positive risk in `notes` — patterns that flag legitimate documentation should be called out so reviewers don't mistake them for hard rules.

## Override audit trail (pre-push only)

When a pre-push scan match is overridden by the user, the inbox file's frontmatter MUST be amended to record the override before push:

```yaml
sentinel_override:
  reviewed_by: <git-user>     # GitHub username from `git config user.name`
  reviewed_at: <ISO-8601>     # UTC timestamp
  patterns: [<name>, ...]     # which pattern(s) were overridden
  matches:                    # RECORD THIS — the matched line excerpts the user reviewed
    - "<excerpt as reported by the hook>"
  justification: <string>     # brief reason supplied by the user
```

With `matches` recorded the override is **excerpt-bound**: it suppresses a listed pattern only on
lines containing a recorded excerpt, so editing the matched line — or a new match of the same
pattern elsewhere in the file — blocks again and must be re-reviewed. An override without
`matches` retains the legacy per-file scope for its listed patterns; treat that as a migration
state, and add `matches` whenever touching one.

This field is recognized by `inbox-entry.schema.json`. Parliament Sentinel sees the override field and **still runs its scan**, but if the same patterns match and the override frontmatter accounts for them, Sentinel logs the override in the run report rather than quarantining. New pattern matches not covered by the override still quarantine.

The override is per-file, per-pattern, and (with `matches`) per-excerpt — re-editing a matched line invalidates its coverage and the content must be re-reviewed.
